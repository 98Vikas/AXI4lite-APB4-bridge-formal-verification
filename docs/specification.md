# AXI4-Lite to APB4 Bridge Specification

## 1. Purpose

This document defines the functional specification of the AXI4-Lite to APB4 bridge.

The specification defines the externally visible behavior that the RTL implementation and verification environment must satisfy.

---

# 2. Scope

The bridge converts supported AXI4-Lite memory-mapped transactions into APB4 transactions.

The bridge operates as:

* AXI4-Lite slave
* APB4 master

The connected AXI4-Lite master initiates transactions.

The connected APB4 peripheral responds to transactions generated by the bridge.

---

# 3. Transaction Model

The initial implementation supports one active bridge transaction at a time.

The bridge does not accept a new transaction that conflicts with an active transaction.

The exact arbitration behavior between read and write requests is defined by the bridge control architecture.

---

# 4. AXI4-Lite Write

An AXI write consists of:

1. Write address transfer
2. Write data transfer
3. APB write transaction
4. AXI write response

The bridge must preserve:

* Write address
* Write data
* Write strobes
* Required protection information
* APB completion status

---

# 5. AXI4-Lite Read

An AXI read consists of:

1. Read address transfer
2. APB read transaction
3. AXI read data response

The bridge must preserve:

* Read address
* Required protection information
* APB returned data
* APB error status

---

# 6. APB Transaction

Each accepted AXI transaction generates an APB transaction containing:

* Address
* Direction
* Write data where applicable
* Byte strobes where supported
* Peripheral select
* Setup phase
* Access phase

The APB transaction remains active until the peripheral indicates completion using `PREADY`.

---

# 7. APB Error Handling

If the APB peripheral asserts `PSLVERR` when the transaction completes, the bridge converts the error into the appropriate AXI response.

The exact response encoding is defined by the implementation and verified through dedicated assertions.

---

# 8. Reset

The bridge uses an active-low reset.

During reset:

* Internal control state returns to the idle condition.
* Active transaction control is cleared.
* AXI response generation is placed in the defined reset state.
* APB control signals return to their defined inactive values.

The reset behavior is verified independently using SVA.

---

# 9. AXI Handshake Requirements

A transfer occurs only when:

```text
VALID && READY
```

The bridge must not incorrectly consume a transaction without a valid handshake.

Signals required to remain stable while waiting for a handshake must satisfy the corresponding protocol requirements.

---

# 10. APB Phase Requirements

An APB transaction follows:

```text
IDLE
  ↓
SETUP
  ↓
ACCESS
  ↓
COMPLETE
```

During SETUP:

```text
PSEL   = 1
PENABLE = 0
```

During ACCESS:

```text
PSEL    = 1
PENABLE = 1
```

The transaction completes when the APB peripheral indicates readiness.

---

# 11. Transaction Integrity

For every accepted transaction:

```text
AXI request
     ↓
APB transaction
     ↓
AXI response
```

The bridge must not:

* Duplicate an accepted transaction
* Lose an accepted transaction
* Corrupt the transaction address
* Corrupt write data
* Corrupt read data
* Generate an incorrect response

---

# 12. Unsupported Behavior

The project explicitly defines the supported AXI4-Lite and APB4 feature subsets.

Unsupported behavior is not treated as a verification hole.

It is documented as an architectural scope limitation and excluded through clearly defined environmental assumptions where necessary.

---

# 13. Parameterization

The implementation will define configurable parameters for applicable:

* Address width
* Data width

The default configuration will be documented in the RTL and verification environment.

---

# 14. Verification Contract

The verification environment shall verify:

### Protocol

* AXI4-Lite handshake rules
* APB4 phase rules

### Functional

* Address integrity
* Write-data integrity
* Read-data integrity
* Response integrity

### Control

* State-machine legality
* Reset behavior
* Transaction completion

### Safety

* No transaction duplication
* No transaction loss
* No illegal protocol phase

### Formal

* Safety properties
* Cover properties
* Reachability
* Environmental assumptions
* Counterexample analysis

---

# 15. Specification Change Policy

Any change to the intended bridge behavior must first be reflected in this specification.

The RTL and verification properties must then be updated consistently.

The specification is treated as the reference for determining whether observed RTL behavior is correct.
